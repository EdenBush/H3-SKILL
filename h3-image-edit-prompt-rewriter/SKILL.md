# H3 图片编辑提示词改写器

## 定位

输入：一到多张参考图（自动编号 `<Picture 1>`、`<Picture 2>`……）+ 一句简短指令，可能非常口语、甚至只是一个想要的结果。
输出：**一段可直接粘贴进 H3 图片编辑模型的英文扩写描述**，三段式结构。

这个技能做的事不是「写提示词模板」，是**写一份对成品图的完整描述**。两者的差别是本质的：

- 模板是给人看的话术（"让她穿上那条裙子"）。
- 描述是给模型看的画面事实（"她上身穿着一件淡粉色蕾丝胸罩，肩带压进肩部……"）。

编辑模型不理解"修改"，它理解"结果"。所有指令都必须先翻译成成品的状态。

---

## 一、地基认知：编辑模型的三个特性

### 1. 它对"否定"没有独立处理分支

H3 系列没有 positive/negative 双条件，`不要`、`no`、`without` 不会进入负向压制，只是普通文本，甚至可能被正向采样。

**所有约束都必须写成可见的确定状态。**

| 想表达 | 写成 |
|---|---|
| 不要原图的文字 | 画面中只出现 `'xxx'` 这一行字，其余区域为纯色 |
| 不要换脸 | 她的脸与 `<Picture 1>` 完全一致，五官、眼镜、发型逐项对应 |
| 不要多一个人 | 画面中恰好一个人 |

### 2. 它对"保留"是默认弱约束

你不说的地方它就自由发挥。所以**保留必须显式声明**，而且要逐个元素声明，不能一句"其余不变"带过。

这就是三段式存在的理由：Part 2 的那一句关系声明，等于给每个元素签一份保留合同。

### 3. 它对"完整描述"最敏感

给它的描述越接近一张成品图的完整视觉事实，执行越稳。所以三段式的 Part 3 允许写得很厚——但**只准写变更范围内**的东西。

写已被判定为"完全保留"的元素，会把它从"保留"降级成"重新生成"，反而变差。这是本技能最重要的一条纪律。

---

## 二、三段式结构

提示词永远是这个形状，顺序不能变：

```
Part 1  参考元素定义     每个要保留/借用/改变的元素，给它一个 <Subject N>，并说明它在哪张图
Part 2  目标概述         一句 "The target image ..."，然后每个 Subject 一句关系声明
Part 3  本次变更细节     只写变了的、新增的，以及它们的物理整合后果
```

三段的职责边界：

| 段 | 回答什么 | 允许写多厚 |
|---|---|---|
| Part 1 | 这些东西在源图里是什么 | 够识别即可，不要复述全貌 |
| Part 2 | 目标长什么样，每个元素是留是改 | 概述段一句话，关系段一句一个 |
| Part 3 | 改成了什么，新增了什么 | 可以很厚，但只在变更范围内 |

### Part 1 的写法

自然语言、元素在前，不暴露结构指令：

```
The woman in a red coat in <Picture 1> is <Subject 1>.
The pale pink lace bralette in <Picture 2> is <Subject 2>.
```

禁止：`Define <Subject 1> as...`、`Let Subject 1 be...`、`Section 1:`、`Identify...`。

必须写 `<Picture N>` 并且是**逐张列名**，禁止 `the reference images`、`the previous images`、`all inputs` 这类模糊指代。

### Part 2 的写法

一句概述，开头必须是 `The target image`：

```
The target image shows <Subject 1> standing in a white studio wearing <Subject 2>.
```

然后每个 Subject **各自独立一句**关系声明，不允许把两个 Subject 合并成一句。

四种关系见 `references/relationships.md`。

### Part 3 的写法

只写三类东西：

1. 源属性里**真的变了**的那些，写它的最终具体外观；
2. 指令**新引入**的人物、物件、文字、环境、布局；
3. 变更带来的**物理整合后果**——比例、朝向、接触、遮挡、投影、反射、光照响应、解剖、支撑、构图。

Part 3 不是重写整张图，是写差值。

## 三、四种保留关系

| 关系 | 判定 | 句式 |
|---|---|---|
| 完全保留 | 身份、外观、数量、姿态、位置、拓扑、角色全都没变 | `<Subject N> is fully preserved.` 独立成句，不加任何补充 |
| 部分保留 | 还能认出来，但至少一个相关属性变了 | 写清留了什么类别、变了什么类别，给"从 A 变成 B"的具体关系 |
| 属性转移 | 某个源属性被复制到另一个载体上 | 点名源 Subject、被转移的属性、目标载体 |
| 弱引用 | 只借一种笼统的气质/风格/配色逻辑，不要求精确匹配 | 点名借的是什么，说明新设计可以在哪里自由变化 |

**判定顺序**：先问"这个元素整体变了吗"，再问"变的是它自己，还是它的某个属性被搬走了"。

一个常见错误：源物件本身没变，只是它的颜色被搬到了别处——这时要**把颜色单独定义成一个 Subject**，让物件的保留和颜色的转移各有归属。否则你会把物件判成部分保留，而它其实一点没动。

另一种错误：母 Subject 里包含了一个被改的子 Subject，却给母 Subject 判了"完全保留"。**母不能全留，除非子也没动。**

---

## 四、Subject 粒度

粒度按**判断范围**切，不按数量配额切。

一条可操作的规则：

> 这个部件需要**自己的保留/变更判断**吗？需要，就单独一个 Subject；不需要，就别拆。

| 情况 | 处理 |
|---|---|
| 人整体穿一件衣服，衣服要换 | 人一个 Subject，衣服一个 Subject（衣服独立被替换） |
| 人整体不动，只有手抬起 | 人一个 Subject（姿态是一个属性，不需要把手拆出来） |
| 衣服换了，同时衣服的颜色来源是另一个图 | 颜色单独一个 Subject（属性转移需要独立归属） |
| 一个人的脸换、发型留 | 脸一个、头发一个，或者人一个 + 说明只变脸（看是否需要分别判定） |

**不要**把普通人机械拆成"脸、头发、手、每件衣服、每个配饰"——它们一起动，就没有独立判断的必要。

十五类可识别的参考元素见 `references/subject-taxonomy.md`。

---

## 五、五条不可违反的纪律

1. **判定为完全保留后，永不再描写它。** 后续句子里只能出现裸的 `<Subject N>` 作为空间锚点，不许带任何形容词、颜色、材质、形状、部件、姿态。
2. **部分保留的 Subject，Part 3 只写变了的属性**，不复述留下的身份、服装、身体。
3. **文字和数据必须逐字写全**，一次，在 Part 1 记录源状态，在 Part 3 写结果状态。不许用"一段文字"、"标题若干"、省略号、"etc."代替。
4. **不许把源图内容重新完整描述一遍**来让段落看起来完整。这是最常见的失败，也是把"编辑"退化成"重绘"的直接原因。
5. **不要为了凑类型而制造 Subject**。十五类是工具，不是清单。

## 六、输出格式

### 默认格式（对话里直接用）

1. **中文标题 + 一句本条的关键判断**（哪些元素留、哪些改、最容易崩的是哪一处）。
2. **素材分工表**：编号 / 提供什么 / 必须排除什么。
3. **提示词代码块**：一段连续英文，无换行、无小标题、无项目符号。
4. **崩点表**：现象 / 修法，3 条左右，只写本条特有的。
5. 可选：一句收尾提问，给两个具体选项。

语言：**描述正文英文，其余中文。**

### JSON 模式（仅当 ComfyUI 节点需要）

节点要求两字段 JSON 时，按 `templates/json-mode.md` 封装：

```json
{"expanded_caption":"...","target_aspect_ratio":"16:9"}
```

注意：caption 内部如果要出现 ASCII 双引号，必须序列化为 `\"`；但按本技能的写法，你应该**用单引号包文字**，从根上避免这个问题。

## 七、H3 图片编辑模型的六个专属坑

这些是视频版 H3 的经验直接迁移过来的，对图片编辑同样成立：

| 坑 | 处理 |
|---|---|
| 角色设定图是多视图 | 必须写 `render exactly one single figure`，并逐项排除分栏、细节裁切块、尺子、标签、水印 |
| 写实参考 + 2D 目标（或反之） | 三件套：槽位排除渲染风格 + 首句钉死目标风格 + 细节处复述风格 |
| 画面内的文字 | 放进单引号，并且逐字给出；不加引号的字会变乱码 |
| 产品平铺图 → 穿在身上 | 必须写受力点与形变（肩带压痕、腰边被撑紧、布料在身体比它宽处起皱），否则布料会浮着 |
| 服装/配饰数量 | 每个可数物都要在锁句里数一遍（一个、两个、十指） |
| 风格词太抽象 | 换成可拍摄的物理描述（`flat cel-shaded colour` 而不是 `anime style`） |

细则见 `references/h3-edit-quirks.md`。

## 八、自检

写完先跑脚本：

```bash
node scripts/check_caption.mjs caption.txt
node scripts/check_caption.mjs caption.txt --json    # 检查 JSON 封装模式
```

它检查：三段是否齐全、每个 Subject 是否先定义后使用、是否每个 Subject 恰好一句关系、完全保留是否用了标准短句、是否在完全保留后又复述外观、是否有结构指令泄漏、是否混入换行、文字是否用单引号。

脚本判不了的，人工过这五项：

1. Part 3 里有没有混进"保留内容的重写"？
2. 有没有哪个 Subject 的粒度明显不对（太粗导致漏改，太细导致碎片）？
3. 新增内容的描述够不够厚（能不能照着画出来）？
4. 文字/数据有没有漏字、错字、翻译了不该翻译的？
5. 所有否定式表述是否都改成了正向状态？

## 十、与其它技能的关系

| 技能 | 分工 |
|---|---|
| `H3-scene-prompt-director` | 管**视频**：时间码节拍、生理动态、镜头设计、一致性锁 |
| 本技能 | 管**静帧编辑**：参考元素定义、保留合同、变更差值 |
| `h3-ref2va-acting-director` | 管 H3 视频的模型机制与多主体身份隔离 |

三者共用同一套 H3 底层认知（无负向分支、结构化描述优先、逐项锁定），但输出物完全不同：一个是带时间轴的分镜，一个是单帧的成品描述。

## 十一、维护约定

- 新踩到的坑先进 `references/h3-edit-quirks.md`，再从坑里提炼规则回 SKILL.md。
- 改自检项时同步改 `scripts/check_caption.mjs`，否则检查会静默失效。
- 三段式的骨架不随模型版本变化；版本更替只改 `h3-edit-quirks.md`。
- 所有示例都要能直接跑，不要写"示意用"的假例子。
